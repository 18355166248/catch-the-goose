# 堆积实验场（lab/）

正式玩法之外的独立跑测场。目的只有一个：**在同一批物件、同一个红木矩形筐、同一套
参数下，让几种物理底层正面比一次堆积效果**，效果确认之后再决定正式工程的架构。

碗形容器不参与本阶段（方案已定：矩形筐达到满意效果后，再专门做连续碰撞碗壳）。

## 目录

```
lab/
  shared/scenario.ts   场景规格（唯一真相源：容器 / 件表 / 缩放 / 落点 / 初速度 / 种子 / 步长）
  shared/metrics.ts    指标采集（落定时间、微颤、互插、覆盖率、抽底扰动）
  shared/harness.ts    跑测外壳（录屏、HUD、阶段机、结果导出）
  poc-b-jolt/          POC B：Three.js + Jolt
  poc-c-havok/         POC C：Babylon.js + Havok
  results/             各 POC 的采数结果
```

POC A（清理后的 Cocos 对照组）住在正式工程里：`game/assets/scripts/lab/`，
用 `?lab=1` 启动，不与 GameManager 共存。

## 跑测

```bash
npm --prefix lab/poc-b-jolt install --registry=https://registry.npmjs.org
```

然后起 dev server（`.claude/launch.json` 里已登记 `lab-jolt` / `lab-havok`），
浏览器打开：

- `?sc=s36&mode=fast` —— 36 件、采数模式（几秒出结果，后台标签页也跑得动）
- `?sc=s56&mode=realtime` —— 56 件、真实速度并录 webm（跑完 HUD 上出下载链接）
- `&proxy=hull` —— 碰撞代理换成凸包（默认 `auto` = 薄片圆柱 / 其余方盒）

结果同时写进 `window.__labResult`，方便脚本抓取。

## 两种模式为什么要分开

`fast` 每个 tick 猛推 240 个物理步，用 `setTimeout` 驱动，不受 rAF 节流影响——
跑测标签页不在前台时 rAF 会被浏览器降频甚至暂停，realtime 模式下仿真会原地不动。
但 `fast` 的画面不是真实速度，录屏没有意义，所以录屏只走 `realtime`。

两种模式的**指标读数一致**：阶段判定挂在仿真时间上，且固定每 6 个物理步（20Hz）
采样一次，与渲染帧率无关。

## 三套 POC 的公共约束

这些是"公平比赛"的前提，任何一套 POC 都不许自行其是：

- 容器、件表、件的缩放、落点、初速度、初始朝向、随机种子 —— 全部来自 `shared/scenario.ts`
- 固定步长 1/120 + 渲染插值（禁止把渲染帧长直接喂给物理）
- **禁止脚本冻结**：物件停下来的唯一途径是引擎自己的休眠
- **禁止改写动态刚体的位置**（正式工程的 `constrainVisualInside` 就是这类改写）
- 相机、灯光构图一致（正交俯视，与正式工程一致）

## 硬验收标准

| 指标 | 门槛 | 采集方式 |
|---|---|---|
| 落定时间 | 2~5s，不能长期蠕动 | `settleTime`（末件投放 → 全体静止且保持 0.5s） |
| 落定后微颤 | 10s 内无肉眼可见位移 | `maxDrift` < 1cm，`jitteryCount` = 0 |
| 穿透 / 爆飞 | 无 | `overlapPairs`、`escapedCount` = 0 |
| 抽底塌落 | 只发生局部塌落 | `removeDisturbRatio` 小比例、`removeResettle` 短 |
| 堆型 | 摊开而不是垒柱 | `pileMedianY`、`coverage` |
| 帧率 | 中端安卓 ≥30fps | `fpsP50` / `fpsP5`（须 realtime 模式） |

另有一条主观门槛：三套录屏没有一套达到认可的效果，就继续改 POC，不迁移正式玩法。

### 指标口径上的两个坑（已修，别改回去）

- **覆盖率**不能用包围球半径算，要用「与底面等面积的圆」半径。用包围球会把
  苹果的投影面积高估一倍，覆盖率虚报到 92%。
- **互插**不能用包围盒对角半长做判据。立方状物件的对角半长比自身大 73%，
  密堆下正常相邻的件会被成片误判（实测 56 件凸包堆虚报 109 对）。现用等效体积
  半径 `cbrt(hx·hy·hz)`。

### 四条结论

1. **Cocos 的问题在引擎层，不在脚本补丁。** 把正式工程的三层兜底（0.9s 定时硬冻、
   PilePatrol 两条冻结判据、constrainVisualInside 位置改写）全部删掉之后，36 件方盒档
   跑满 45 仿真秒**一件都没休眠**——32 件处于 Bullet 的 `WANTS_DEACTIVATION`（想睡），
   却因为休眠按**接触岛整体判定**（一件不静，全岛不睡）永远跨不过去。密堆下 36 件同属
   一个岛，香蕉这类被方盒粗暴近似的长条件始终找不到稳定支撑，一件拖着 35 件一起醒着。
   那些硬冻代码是在给这个「永不收敛」擦屁股，不是多余的——删了不会变好，只会露馅。

2. **换 PhysX 救不了。** 同样从未落定（auto 档 3/36 休眠、hull 档 0/36），还额外出现
   半空悬停：apple_23 停在 y=6.36（比围栏顶还高）、速度 0、已休眠，永远吊在那儿。

3. **凸包代理是堆型的决定因素。** 三套引擎换上凸包后堆顶都从 2.8~3.5 掉到 1.3~1.5、
   覆盖率涨到 87~90%。方盒把水果撑成方块、互相架桥垒成柱。正式工程现状正是只有
   Box/Cylinder（GameManager.ts:905），这条在正式工程里同样成立。

4. **Bullet 用不了凸包，PhysX 可以。** Cocos 的 MeshCollider 只吃现成 Mesh、没有喂点集
   的接口，只能整网格进引擎。Bullet 拿到多少顶点用多少 → 单步 18.97ms（36 件）/
   34.42ms（56 件），桌面 Mac 就已慢于实时 2~4 倍；PhysX 在 cook 阶段压到 255 顶点上限
   → 0.507ms，可用。但性能可用不等于结果可用，它照样不落定。

### 帧率（realtime，56 件凸包，桌面 Chrome）

| | 落定(s) | fps p50 | fps p5 | 单步(ms) | 覆盖率 | 录屏 |
|---|---|---|---|---|---|---|
| Jolt | 1.45 | 59.88 | 56.82 | 0.05 | 88.2% | `jolt-s56.webm` |
| Havok | 4.30 | 59.88 | 58.48 | 0.20 | 83.3% | `havok-s56.webm` |

两种模式的物理读数完全一致（落定时间、位移、抽底扰动都对得上），说明 fast 模式的
采数可信，不是"跑快了所以好看"。

### 排名

Jolt 与 Havok 都干净通过硬门槛：落定 1.45s / 4.30s（窗口 2~5s），落定后零位移，
零互插零逃逸，抽底 0% 扰动，桌面稳 60fps。**Jolt 明显更优**——落定快 3 倍、单步快
4 倍、覆盖率高 5 个点；Havok 的 4.30s 已经贴在验收窗口上沿。

Cocos 两个后端都未通过：Bullet 与 PhysX 都跑不出落定。
