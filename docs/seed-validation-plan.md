# 种子用户验证方案

## 样本与周期

- 20～50 名未参与开发的玩家。
- 连续开放 7 天；同一发布版本至少稳定运行 48 小时后再比较难度。
- 每位玩家只需获得预览链接，不提供玩法讲解，避免污染首次引导结论。

## 核心漏斗

1. `app_boot → physics_ready → home_view`：启动健康度。
2. `home_view → round_start`：首页到开局转化。
3. 按 level 统计 `round_start → round_end(win)`：三档完成率。
4. `round_exit`、失败 reason、`rescue_use`：中断与挫败来源。
5. `runtime_error`、`asset_load_failed`、`remote_asset_fallback`：技术质量。

埋点只提供会话级行为，不构造跨日用户画像。次日回访通过种子名单的匿名编号问卷统计，
不把手机号、账号或设备标识写进游戏事件。

## 每日检查

- 使用 `node tools/analyze-telemetry.mjs <导出的 events.json>` 生成简报。
- 错误事件逐条归因；技术错误率未收敛前不调数值。
- 样本不足 20 人或单难度结算少于 30 局时，只记录趋势，不做版本决策。

## 结束问卷

- 是否在 30 秒内理解目标？
- 最难辨认的是哪类物件？
- 失败更像时间不足、槽位决策错误，还是点击/遮挡问题？
- 四个主题最想再玩哪个？
- 第二天是否主动再次打开？若没有，主要原因是什么？
